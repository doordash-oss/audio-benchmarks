Order-Up-Bench

Order-Up-Bench

Problem Setting

With the advent of “speech-to-speech” models trained to natively process text and audio inputs and outputs, more applications are making use of the capabilities to support more natural user-agent interaction. This additional capability can come at the cost of interpretability when trying to measure model performance. Where a cascaded ASR → LLM → TTS pipeline allows for error attribution at a specific pipeline stage (e.g. “transcription error”, “reasoning failure”, “intent misclassification”), a single end-to-end model is a black box which can only be evaluated end-to-end.

To address this problem, evaluation benchmarks have been developed to stress an agent’s ability to accomplish a task by building some structured output in response to an audio message or a sequence of messages. Full Duplex Bench V3 builds a dataset of audio clips containing simulated customer requests and tasks the agent with coming up with the correct set of tool calls based on the request. The user speech contains disfluencies representing a customer hesitating or changing their mind which are more common in speech than in the text modality. Speech samples may require multiple tool calls in sequence or may contain a set of corrections or revisions to earlier parts of the speech, but the entire clip is played in a single utterance without waiting for the agent’s response.

In an earlier work, Full Duplex Bench V2 attempts to model the real-world challenges associated with the multi-turn setting by using a second agent generating synthetic customer requests and follow-ups instead of a recording. This allows the customer to represent more complex multi-turn behavior, but it is hard for synthetically generated speech to capture the features that make natural speech audio a challenging domain.

This benchmark, Order-Up-Bench, tries to combine the natural speech disfluencies and the multi-turn evaluation setting of the previous approaches. Specifically, we measure the capability of an agent to build a virtual “cart” for a restaurant order when played against an “examiner” agent playing the role of customer. The examiner does not generate any speech itself. Instead, after each agent response, the agent emits a tool call containing the ID of the next audio clip to play, and then a fragment of audio from a real recording is played and fed to the agent, simulating a dialog between an agent and a human speaker.

Evaluation

Food Ordering

The food ordering domain provides several challenges which make it a good candidate for benchmarking speech-powered agents. When entering structured data into a system for recording orders, there is often no flexibility in representation — the items in the order must appear exactly as they appear in the menu with all the required options selected. Often a customer’s request doesn’t map cleanly to exactly one combination of items and options from the menu. In that case, the agent must judge whether to find the closest match on the menu and assume what the customer means or to ask a follow-up question to get more information. This setting naturally lends itself to turn-taking.

In the specific prompt and tool set the model has access to, the possible actions are “add an item to the cart (with options)”, “remove an item from the cart”, or “submit the order”. Items on the menu have options and required choices. Required choices can have defaults, and a required choice with no defaults requires the agent to collect the information about that choice from the customer.

Multi-turn Harness

The agent in charge of playing clips is given access to a fairly simple decision tree describing how to play the available clips. First, play the clip for a given item. If the agent asks a follow-up question about that item, if the clip player has access to a relevant response for that question for that item, play it. If there is no question or no matching answer, move on to the next item or for any pending “corrections” for the current item (i.e. play a clip where the customer says “Actually I want <item> instead”). The customer clip player agent is tuned so that it waits to emit its next response until it detects the agent has finished speaking, reducing (but not fully eliminating) the possibility of interruptions of the agent by the customer. In general we’re more concerned with how often the agent interrupts the customer than how the agent responds to being interrupted by the customer.

Some customer clips contain speech for multiple items in one clip or for an item and its correction all without a gap in between. In these cases the agent must produce the correct sequence of outputs for the request, not just a single tool call.

Based on the expected sequence of played clips, we construct a “ground truth” cart and compare it to the cart produced at the end of the session.

Why multi-turn?

It’s worth asking what benefit there is for running this multi-turn evaluation vs running a simpler single-turn evaluation against each turn of the conversation clips and aggregating the scores. The multi-turn framework has the opportunity to surface some issues which would be difficult to surface in single-turn evals:

  • Single-turn evaluations penalize models for waiting for certainty before modifying the cart. Instead of having to make a binary decision for a label for each utterance for whether a tool call should happen immediately after each message, we can allow the agent to decide and to follow-up, and explicitly measure the trade-off of success rate vs time to complete the session.
  • Accounting for the customer’s “theory of mind” is an important criterion for successful speech agents. In scenarios where a customer asks for multiple items/options/corrections in a single utterance, a speaker is not always 100% certain that their counterpart heard or understood them correctly. If the agent fails to convey to the customer that they understood their full message, the customer may repeat themselves or restate their order in a different way. We need to then measure how the agent handles this follow-up and if they can successfully reconcile both speakers to the same understanding of what’s been ordered so far.
  • More turns means more opportunities to diverge from strict turn-taking behavior and encounter cases where the precise timing of utterances has a significant impact on meaning. For example, if an agent asks two or more questions, the precise timing of the customer’s response is important to the meaning. If an agent asks “Would you like anything else? Is that all?”, then a “no” response has opposite meaning if “no” arrives before/after the “is that all?”. Can an agent reconcile which question an answer was in response to?
  • It’s hard to predict the cascading nature of errors and their effects on the final result without running a full conversation. Consider a case where VAD is firing too aggressively on noise after a customer request, which leads to the agent taking too long to respond, which leads to the customer repeating their order unsure if the agent heard it, which leads to the agent incorrectly assuming the customer is asking for a second order rather than restating their first — individually we can measure some of these error rates but not necessarily say how they’ll affect the end-to-end system.

Data Complications

The recordings that were spliced to generate the clips for each scenario were collected from two-player interactions with a “game” UI showing one player which items to order verbally for their partner to put into a UI. The partner’s UI can then show them if there are any required options missing so they can ask a follow-up and induce their partner to respond with a natural sounding answer. The UI also tells the “customer” player randomly to correct their options to something else. Instead of providing a specific script with pre-determined phrasing, the UI and the nature of the two-player interaction provide a scaffold for what content to discuss but leave the actual phrasing up to the players. Two players are free to communicate about the items that need to be ordered in whatever way they want as long as they accomplish the task by building the right cart in the end.

This collection method gives us a variety of different speech patterns:

  • All items ordered in a single utterance
  • Item + correction ordered together
  • One item at a time with “agent” player acknowledgement in between
  • Separate item order + option clarification utterances

In addition to those content-related features, the collection process samples from a variety of users across different devices, accents, and background noise environments.

Dataset composition

The working set for the V1 benchmark is 248 per-stage tasks drawn from 64 recording sessions spanning 15 distinct restaurants, recorded by 49 contributors.

The distribution is long-tailed: a small number of contributors recorded many sessions, while the median contributor accounts for 3 stages.

Results

Metrics

Headline numbers now come from 3 independent sweeps of each model over the same 248 per-stage tasks (run against the published Hugging Face dataset under identical conditions, after the audio-bridge timing fix).

Each model contributes 3 runs per task, so per-task outcomes carry real run-to-run variance: re-running the same model on byte-identical data moved individual tasks in both directions and shifted aggregate pass rates by several points sweep-to-sweep. Rates below are reported as the mean across the 3 sweeps, ± half the min–max spread across those 3 sweeps. Treat small gaps between models as inconclusive.

Success rate

A run counts as a clean pass when the agent’s final cart matches the ground-truth cart exactly on that attempt — every expected item present, no extras, no wrong options or variants, and no fallback/recovery clip was ever needed. The denominator is 248 (all tasks) for every model.

This is a stricter bar than the single-sweep “success rate” reported previously (which counted any successful cart, including ones reached only after a recovery clip fired) — see the Effective Success Rate & Duration section below for a version that credits partial/likely-correctable outcomes.

Recoverability

Among the conversations with a cart mismatch against ground truth, not all failures are equal in severity. When an agent deviates from the expected trajectory, our customer simulator agent has some limited capability to steer the conversation back on track. For example, a common failure mode among all models is asking unnecessary clarifying questions to which the original reference audio has no answer. Specifically, if the agent asks about a required option choice which has a default value, the prompt instructs the agent not to ask about that group and to let the backend fill in the default values. If the agent goes off-policy and asks a superfluous question, we give the customer model access to a special clip with audio saying “just the defaults”. In certain scenarios, playing this clip can help the conversation converge to the expected trajectory, and we mark this conversation as “recovered”. Because we limit the scope of possible repairs to keep the clip player/customer player predictable and consistent, there are situations where the agent deviated from the expected trajectory in a way where a real customer could correct the agent and steer the trajectory back to the expected cart, but the simulated customer cannot. These evaluated conversations are marked as “recoverable”. A prime example of this case is when the agent adds the wrong item to the cart but reads back clearly what they added. A real customer could in theory hear this and ask the agent to make a correction, but this is not guaranteed. Finally, some conversations are “unrecoverable”. Generally these are stages where an agent silently adds or drops an item without acknowledging to the customer what they did. (See the error breakdown section for more detail about recoverable vs unrecoverable issues.)

Effective Success Rate & Duration

The clean pass rate and recoverability buckets above treat every non-clean outcome the same regardless of severity, and don’t credit a “recoverable” run for the fact that a real human customer, unlike our simulated clip player, might have caught and corrected the agent’s mistake mid-conversation. Effective success rate puts a number on that: it assumes some fraction of “recoverable” runs would have been corrected by a human in the loop, and credits that fraction of a success. We report two anchors:

  • effective@50 — assumes a 50% chance a human would notice and correct a recoverable failure: (passed + recovered + 0.5 × recoverable) / total.
  • effective@100 — the optimistic bound, crediting every recoverable failure as if it were always caught and corrected: (passed + recovered + recoverable) / total.

Both are computed per sweep, then averaged across the 3 sweeps (± half the min–max spread), over the full 248-task set per model — same denominator as the clean pass rate table above.

Effective duration estimates the average time cost per task if recoverable failures were corrected in-conversation, rather than the clean “all-pass-intersection” duration reported in the timing table below. For each task, we average the game duration of every valid run (passed/recovered as-is; recoverable runs scaled up by a recovery time factor of 1.35×, since off-script-but-successful “recovered” runs in this dataset take ~35% longer than clean “passed” runs on the same task, estimated from 203 same-task/same-provider passed-vs-recovered pairs after 1.5×IQR outlier filtering). Runs where a task never had a valid outcome for a given model are excluded; to keep the comparison apples-to-apples across models, the sample set is further restricted to the 245 (of 248) tasks where every model had at least one valid run.

Effective # of turns applies the same logic to conversation length: the average number of customer turns per task, with valid runs counted as-is and recoverable runs scaled up by a recovery turn factor of 1.39× (recovered runs take ~39% more customer turns than clean passed runs on the same task, estimated from 193 pairs with the same filtering). It uses the same 245-task sample, so it can be read directly against effective duration.

The narrow gap between effective@100 and a perfect score for Gemini/Grok/Cascaded (all at 96–98%, since almost every non-passed run is “recovered” or “recoverable” rather than “unrecoverable”) shows that most of those models’ failures are, in principle, fixable in a real conversation — OpenAI’s and Cascaded’s lead on clean pass rate is mostly about how often the simulated customer or a real one would need to step in, not raw task competence.

Effective duration and effective # of turns move together because they are built from the same runs with nearly the same scaling: effective turns × the average time per turn on those runs lands within about 2% of effective duration for every model. The differences between models therefore decompose into how many turns a conversation takes and how long each turn lasts. OpenAI Realtime wins on both; Gemini needs the most turns but has the shortest ones; Grok has moderate turn counts but the longest turns (long agent responses); Cascaded’s turns are dominated by response latency (about 6.3s per response, against 3.7–4.8s for the others). Restricting duration to correct and recovered runs only (no scaling, 175 tasks where every model has at least one such run) gives 47.7s / 50.1s / 65.7s / 58.0s for OpenAI / Gemini / Grok / Cascaded — about 15–18% lower, with the same ordering.

Turn-taking

In addition to success rate, we track metrics for conversational fluency - how often does the agent interrupt the customer or fail to respond: An interruption is a clear case where the agent began speaking while a customer clip was still mid-utterance (agent VAD speech-start during customer audio). No response counts clips after which the agent stayed silent past the 8-second clipPlayer watchdog.

Clip plays and events below are pooled across all 3 sweeps per model (not averaged per-sweep) to get a larger, more stable sample for these low base-rate events.

Timing metrics

In addition to the turn-taking metrics, we also look at timing statistics:

  • Latency: How long after a clip ends does it take for the agent to respond (measured from the customer’s last audio frame to the agent’s first speech token)
  • Response duration: Once the agent starts speaking, how long does it talk until it hands the conversation back over to the customer?
  • Game duration: How long does it take to complete the conversation? (wall time from the end of the agent’s first turn to the last speech event, minus customer-side pauses) Averages are computed over the all-pass intersection (task-runs where every model scored 1.0 within the same sweep, pooled across the 3 sweeps) so that we filter out cases where the model went off-policy. Game duration captures both the time spent per turn and the total number of turns. A model which quickly responds to each question but takes extra turns meandering through unnecessary questions can lead to a worse experience than a model which takes more time to think for each turn but asks targeted questions which lead to a conclusion faster.

Failure-tag breakdown

Imperfect-run cart-diff tags are split into three plots. Silent adds/swaps — the agent committed a wrong/extra value to the cart without ever speaking it back; the customer had no way to catch the mistake. Read-back adds/swaps — the agent verbalized the value but the value was wrong, so the failure mode is reasoning/transcription rather than silent mis-tool-use. Missing items — items the agent never added at all, with the customer absorbing a follow-up burden.

Tag totals are occurrence counts — a single imperfect run can sit in more than one plot if its cart diff carries multiple categories. Counts below are the average per-sweep occurrence count across the same 3 sweeps used throughout this section, rounded to the nearest whole occurrence.

Preemptive item add — it fires when the server-side VAD tripped before the first customer clip even played, meaning the agent emitted a tool call without having heard the customer at all. Most preemptives ride alongside an extra-item tag (the fabricated item) but the same audio condition can produce a wrong-item instead, so the preemptive bands are split out across both.

The three item-level cart-diff categories cover distinct kinds of mismatch:

  • extra-item — the agent added an item the customer never ordered, in addition to the expected items. The cart contains more rows than it should. (unrecoverable if silent else recoverable)
  • wrong-item — the agent ordered something instead of the right item; the row count is right but the menu base_id (the catalog identity, e.g. “burger” vs “chicken sandwich”) doesn’t match. (unrecoverable if silent else recoverable)
  • wrong-option-or-variant — the base_id matches but a required option (e.g. size, spice, sauce) or a price-bearing variant resolved to the wrong value. The agent picked the right thing on the menu but not the right configuration of it. (unrecoverable if silent else recoverable)

The bands carry the same three item-level categories as the silent plot — extra-item, wrong-item, wrong-option-or-variant, plus the preemptive split on the extras. The difference is that here the agent spoke the wrong value (e.g. read back the cart, repeated the item, or summarized) before or after committing. Read-back failures are typically easier for a downstream system to flag because the audio transcript records the agent’s belief, whereas silent failures only appear when the cart is inspected.

A missing item is a row in the expected cart that the agent never added. The plot bands name the reason the post-eval auditors landed on for that omission:

  • not-detected — the missing item’s main customer clip played in full, then the agent stayed silent until the clipPlayer’s 8-second watchdog force-kicked the session. This is the “didn’t hear it” failure: VAD never tripped or the model couldn’t parse the utterance into a tool call. (unrecoverable)
  • premature submit — the agent emitted submit_order before all expected items had been added. Common shape: the customer was still mid-list when the agent took the silence between items as end-of-order. (recoverable — a more well-equipped agent would be able to un-submit and add new items if the customer clearly communicated more items)
  • clarify abandoned — the agent asked a clarifying question about the missing item, the conversation moved on (often because the customer’s answer didn’t route back to that item), and the item was never added. The agent recognized the item existed but lost the thread. (recoverable — a real customer might respond to the question before asking for their next item)
  • compound line — the customer named multiple items in a single utterance and the agent only captured some of them. The audio for the missing item is present but co-located with audio that was handled. (unrecoverable)
  • other / unattributed — the auditor ran but couldn’t fit the failure into any of the categories above. Includes mixed cases (e.g. an interrupted clarify that’s hard to label) and idiosyncratic agent behavior that doesn’t have a named bucket yet. (marked recoverable since there’s no clear reason to say it wouldn’t be recovered)

The missing-answer bands cover a related-but-distinct failure mode: the customer clipPlayer ran out of clips to play because the agent kept asking a question the clip library couldn’t answer, then auto-submitted the order. The item is missing because the agent was stalled, not because the agent missed the customer’s request. We mark these conversations as recoverable since the failure was with the customer limitations, not the agent.

  • missing-answer · off-policy ask — the agent stalled by asking about an option that policy says shouldn’t be asked (an option group with a default value, or an optional group). The agent’s question is the bug.
  • missing-answer · on-policy — the agent’s question was legitimate (required group, no default) but the clip library happened not to carry a customer-side answer for that specific ask. The gap is in the dataset, not the agent.

Malformed tool calls

When the agent issues an invalid tool call — unknown item_id, options that don’t match the menu schema, an unknown tool name, or malformed JSON — the tool server returns ok: false with an error message. The metric below counts the share of stages where the model emitted at least one such call; one bad call followed by a clean retry is enough to flag the stage.
